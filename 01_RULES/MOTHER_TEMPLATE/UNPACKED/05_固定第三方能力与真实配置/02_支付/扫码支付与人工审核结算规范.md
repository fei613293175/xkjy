# 扫码支付与人工审核结算规范

## 1. 能力定义

人工扫码不是“支付成功即自动回调”的在线通道，而是统一收银台内的 `MANUAL_QR` profile：

- `ALIPAY_QR`：支付宝扫码；
- `WECHAT_QR`：微信扫码；
- `QQ_QR`：QQ 扫码。

它必须复用统一订单、统一金额快照、统一权益发放和统一返佣逻辑。项目应为每个方式配置 `allowed_business_types`；默认覆盖该项目所有允许人工审核付款的真实消费订单，不能把权益结算写死为某一种商品。

## 2. 用户流程

1. 用户选择商品/服务，由服务端创建订单并计算应付金额。
2. 原生收银台按订单类型返回可用支付方式。
3. 用户选择某种扫码方式并确认支付。
4. 后端查询该方式下启用、文件可用的多个收款码，使用随机顺序返回。
5. 弹窗显示订单金额、扫码提示、收款码轮播、保存到相册入口，并固定显示：`支付完成后，请截图付款记录并返回提交审核。`
6. 用户可左右选择其他收款码；当前码 ID 和实际付款截图一起提交。
7. 截图上传到私有对象存储，完成文件签名和 MIME 校验后建立付款提交记录。
8. 用户在“我的订单”查看 `待审核`、`已通过`、`已拒绝` 及拒绝理由。
9. 后台查看受控原图并通过或拒绝。
10. 通过后服务端调用统一业务结算器发放商品/服务权益和返佣；拒绝后不发放，允许用户重新提交有效凭据。

## 3. 收款码管理

- 后台每种方式可上传多个二维码图片，字段至少有 `method_code`、`file_id`、`label`、`active`、`sort_order`、创建/更新时间。
- 上传使用票据式直传或服务端受控上传；`file_objects.business_type=PAYMENT_QR`。
- 只有 `AVAILABLE/BOUND` 且实际文件签名为 PNG/JPEG/WebP 的对象可展示。
- 删除采用停用，历史提交仍保留原收款码引用；不能物理删除已被订单引用的文件。
- 返回列表可采用数据库随机排序；客户端允许轮播全部候选码，首次展示项必须来自本次随机结果。
- 未配置可用收款码时返回 `PAYMENT_QR_UNAVAILABLE`，收银台应显示当前方式暂不可用。

## 4. 付款截图

- 上传业务类型固定为 `PAYMENT_SCREENSHOT`，对象拥有者必须是当前用户，业务 ID 必须绑定当前订单。
- 只接受项目配置允许的图片类型和大小；检查扩展名、Content-Type 与文件签名一致。
- 提交时再次检查订单归属、有效期、订单类型、支付方式可用性、收款码方式一致和截图状态。
- 截图 URL 不公开直链；后台查看接口鉴权后读取对象并返回 `Cache-Control: private, no-store`，每次查看写审计日志。

## 5. 提交与并发

- 同一支付订单只有一条逻辑提交记录，通过唯一约束保证；首次插入，拒绝后重新提交更新文件并递增 `version`。
- 已通过、已完成、已取消或已过期订单禁止再提交。
- 后台审核必须携带当前 `version`；版本不一致返回 `VERSION_CONFLICT`，防止两个管理员重复处理。
- 审核通过操作只能从 `PENDING_REVIEW` 进入 `APPROVED`；拒绝只能进入 `REJECTED`。

## 6. 统一结算事务

审核通过不是简单修改订单状态，必须在同一数据库事务内：

1. 锁定付款提交、支付订单和业务订单。
2. 核验订单金额、状态、用户、支付方式和提交版本。
3. 调用 provider-agnostic 的统一结算器。
4. 发放商品或服务权益。
5. 根据业务规则计算并写入上级返佣/佣金账户；无返佣的订单也写明确结算结果。
6. 把支付订单改为 `COMPLETED`，写 `paid_at`、`entitlement_granted_at`。
7. 把提交改为 `APPROVED`，写审核人和时间。
8. 写 `MANUAL_QR_APPROVED` 支付事件和后台审计日志。

权益使用 `order_id + benefit_type` 唯一键，返佣使用来源订单唯一键。任何步骤失败必须整体回滚，不得出现订单完成但权益或返佣遗漏。

## 7. 审核拒绝

- 拒绝理由必填或使用后台配置的默认理由；
- 写审核人、时间、理由、版本和 `MANUAL_QR_REJECTED` 事件；
- 订单回到允许重新支付/提交的状态；
- 不发放权益、不发放返佣、不把付款截图当作支付成功证明；
- 保留旧截图和审核审计，重新提交后旧版本不可再通过。

## 8. 页面和文案

- 扫码弹窗遵循当前项目全局 UI Token，不制作独立视觉体系。
- 金额必须突出且为服务端返回值；二维码保持正方形，不裁切、不拉伸。
- “支付完成后必须截图上传付款记录”必须在二维码上方或下方持续可见，不能只放在一次性 Toast。
- 支持保存到相册、选择/拍摄截图、上传进度、失败重试、提交中、待审核、通过、拒绝和过期状态。
- 系统相册/权限返回后保留订单、方式、当前二维码和已选图片，不创建重复订单。

## 9. 安全与风控

- 后台审核权限分为 `payments.view` 和 `payments.manage`；查看截图也必须审计。
- 同一截图文件不得绑定多个订单；可增加感知哈希/文件 SHA-256 重复告警，但不能只靠图片哈希自动判定付款。
- 记录订单号、金额、用户、收款码、提交/审核时间和审核人；敏感截图按项目留存策略清理。
- 禁止客户端上传金额、商品权益、返佣金额或审核结果作为可信字段。
