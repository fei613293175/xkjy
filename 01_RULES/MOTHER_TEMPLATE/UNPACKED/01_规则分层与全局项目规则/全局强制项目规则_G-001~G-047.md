# 全局强制项目规则 G-001~G-047

以下规则对通过本母版生成的所有项目无条件生效，覆盖整个项目，不属于任何可选功能模块，也不允许通过模块开关关闭。

### G-001 正式商业产品结构

任何项目从第一天按正式商业 App 结构制定和开发。禁止制作后续需要推倒重做的测试前端、测试后台或测试数据库；禁止用户界面出现 demo、test、mock、调试、接口占位等不适合普通用户的词语。

### G-002 全项目覆盖边界

本规则集覆盖整个项目，不限于五项固定第三方能力。Android App、管理后台、H5、后端、数据库、API、缓存、队列、定时任务、第三方适配、项目专属业务、部署、测试和交付均受 G 规则约束。

### G-003 项目事实源

项目需求、范围、版本和完成状态以仓库中的 PROJECT_CONTEXT、CURRENT_RELEASE、FEATURE_MATRIX、PAGE_INDEX、RESOLVED_RULESET 和 RELEASE_MANIFEST 为唯一事实源，不依赖长对话记忆。

### G-004 规则冲突和覆盖

项目所有者最新明确指令优先。任何全局规则覆盖必须写入 RULE_OVERRIDE_REGISTER，记录原话、原因、生效范围和替代要求；模型不得根据个人偏好静默修改。

### G-005 按需模块化

仅把当前项目启用的条件模块写入项目包。未启用模块不得进入功能清单、页面、API、数据库、后台菜单、配置、测试和版本计划。G 全局规则不因模块关闭而失效。

### G-006 服务器统一开发

Codex 使用已连接的 obx-test SSH 服务器完成项目代码、数据库、后端、管理后台、Android 构建、非设备测试和部署。

### G-007 禁止本机搭建环境

未经项目所有者明确授权，禁止在 Codex 电脑本机安装、搭建或运行项目构建环境、Docker、模拟器、虚拟设备或项目服务。

### G-008 复用现有服务器能力

服务器为 CentOS 8，已具备 Docker 和 Android APK 构建环境；不得无故重复安装整套环境或以环境重建代替实际开发。

### G-009 唯一子域名

所有项目基于 orbexa.cc 规划带项目专属标识的唯一子域名，制作项目文档时先完成域名清单和冲突检查，等待项目所有者解析后再上线。

### G-010 启用模块的真实测试配置直接复用

凡项目启用母版固定第三方能力，必须直接使用该模块已有真实测试配置完成联调；不得重复询问，不得在没有明确错误证据时改成 mock。关闭模块不复制配置。

### G-011 密钥只在后端使用

明文密钥可以存在于私有母版、私有项目包和服务器配置；不得编译进 APK、管理后台前端、H5 静态资源或公开仓库，不得出现在日志和用户接口响应中。

### G-012 每个可视化页面必须有 Page ID

Android、管理后台、H5、独立弹窗、抽屉和选择器必须拥有唯一 Page ID，并写入页面索引和版本清单；页面内部加载、空、错误、成功等使用 State ID，避免把同一路由重复计算为多个页面。

### G-013 每个页面必须有完整规格

每个页面必须记录业务目标、角色、入口、出口、字段、组件、交互、校验、状态、权限、API、数据库、后台配置、日志、埋点、测试路径和视觉验收点。

### G-014 每个页面必须写实际 UI 数值

每个页面必须写明字号、字重、行高、颜色、圆角、边距、间距、高度、宽度、图标和阴影等实际数值，同时标注 Design Token。禁止只写模糊描述。

### G-015 每个页面必须有确定性效果图

项目开发文档确定后，必须使用 HTML/CSS/SVG + Design Token 为每一个 Page ID 及其必要 State ID 生成独立 PNG 效果图和源文件，禁止拼图、仅给概念图或遗漏后台页面。

### G-016 前后端一一绑定

每项功能都必须说明 App/H5 页面、管理后台页面、API、数据库表、权限、配置项、日志、异常状态和测试用例之间的绑定，禁止只描述前端或只描述后端。

### G-017 管理后台企业级标准

管理后台必须按大型公司 App 平台标准开发，保证易用、可观测、可控、可审核、可追溯；禁止随意拼接、粗糙模板化和只有简单 CRUD。

### G-018 后台统一可操作性

后台列表和详情必须按业务需要支持搜索、组合筛选、排序、分页、列配置、关联数据、批量操作和业务时间线；高风险操作必须确认并记录原因。

### G-019 后台统一可观测性

重要业务和第三方服务必须展示状态、关键指标、响应时间、错误数量、最后成功时间、任务状态、失败记录和必要告警，便于运营快速定位异常。

### G-020 后台统一可控性

项目实际存在的功能开关、费用、额度、有效期、模板、频控、业务规则，以及已启用模块中的支付方式、接口配置和保留策略，必须尽可能后台可配置，并有类型校验、默认值、权限、测试和变更历史。

### G-021 后台统一审计性

用户、内容、订单、配置、权限和其他关键业务操作必须记录操作人、时间、IP、原因、对象、修改前值和修改后值。

### G-022 防漂移但禁止重治理

项目必须具备机器可读防漂移状态，但不得建立导致 Codex 长时间只检查、验证、自证而不编码的重治理流程。每次执行必须有实质性编码、部署、修复或测试工作。

### G-023 版本数量控制

除特殊情况外，一个项目尽量控制在 15 个小版本以内；版本按可交付业务闭环划分，禁止为了数量拆分无意义的小任务。

### G-024 单版本单目标

每个小版本由 Codex 设置一个清晰 /goal，只处理该版本范围；完成后关闭目标、更新状态并等待项目所有者安排。

### G-025 真机预检和多设备调度

Android 开发开始时检查本机已有 ADB 和三台真机可用性；版本交付前必须选择状态严格为 device 的空闲真机安装并启动 APK，多台设备应灵活调度。

### G-026 禁止模拟器替代

真机不可用或被其他项目占用时应排队或停止设备测试，不得改用模拟器或虚拟设备冒充真机验收。

### G-027 真机业务与视觉验收

逐页执行点击、输入、返回、滚动和关键流程，检查崩溃、ANR 和日志异常；逐页截图并与效果图比较布局、字体、颜色、间距、图标和交互状态。

### G-028 未通过不得交付

关键功能、适用第三方接口、视觉验收或证据任一未通过时，不得报告完成或通过，不得把 APK 作为合格版本交付。

### G-029 设备释放

真机测试结束后必须释放设备占用状态并返回手机主界面，确保其他项目可以继续使用。

### G-030 中文桌面交付

每个 Android 版本将 APK、原始功能清单与完成清单对比、自动测试报告、真机测试报告和项目所有者测试说明统一放到电脑桌面，目录和文件名使用中文。

### G-031 交付内容可核验

每项“完成”必须可通过页面、接口、数据库、日志、截图或测试步骤核验。不得用文字声明代替实际证据。

### G-032 历史构建清理

本机最多保留最近 2 份旧构建交付物，服务器最多保留最近 5 份旧构建交付物。清理仅针对无用构建、缓存和旧交付包，不得删除正式业务数据、订单、审计记录和当前回滚所需版本。

### G-033 异常恢复

会话中断或转交其他 Codex 时，必须从仓库状态文件、当前代码、部署状态和最近报告恢复，禁止依赖原会话记忆或重新从头规划。

### G-034 只交付已确认范围

完成当前版本后不得擅自扩展新功能、重构无关模块或更改已确认 UI；改进点写入候选清单，等待项目所有者安排。

### G-035 项目所有者测试说明

每个版本必须提供非技术化、可逐步执行的项目所有者测试说明，写清入口、账号、操作、预期结果和异常反馈位置。

### G-036 统一 API 协议、错误码与最小安全边界

所有自有 API 必须采用统一请求、鉴权、对象权限、分页、时间、金额、枚举和响应结构，并返回稳定业务错误码、`request_id` 与服务器时间。正式接口只允许 HTTPS，CORS 使用白名单；Cookie 鉴权的管理后台写请求必须防 CSRF。前端不得直接展示后端异常堆栈、数据库错误或第三方原始错误；接口合同必须可机器读取，并与页面、权限、数据表和测试绑定。

### G-037 Android 签名、版本与最小在线升级

只要项目包含 Android App，就必须从首个可安装版本固定 `applicationId`、正式签名、`versionCode`、`versionName`、构建环境和签名证书指纹，并建立最小可用的版本发布与更新能力：后台发布 APK、更新说明、可选更新、强制更新、最低可用版本和 APK SHA-256 校验。默认不建设复杂灰度、A/B 或多渠道平台。

### G-038 数据库迁移、基础备份与可恢复

只要项目包含数据库，所有结构和关键数据变更必须通过可追踪迁移文件完成并绑定版本；发布前必须备份，正式环境必须具备基础定时备份、恢复说明和回滚路径。允许使用一次性隔离容器或临时数据验证迁移，验证后销毁，不得因此维护一套长期演示环境。

### G-039 结构化日志与基础健康检查

后端必须统一记录 `request_id`、用户或匿名会话标识、API、Page ID、耗时、结果、错误码和时间；必须提供服务、数据库、关键任务和已启用第三方接口的基础健康检查。第一版只要求可定位问题的最小日志和状态面板，不强制建设完整分布式追踪或大型监控平台。

### G-040 最小配置中心与紧急开关

项目实际运营中可能调整的开关、价格、次数、有效期、频控、模板、上传限制和关键业务规则必须进入统一配置中心，并支持类型校验、默认值、权限、变更历史和必要回滚。必须具备维护模式和关键功能紧急关闭能力；禁止把所有 UI 数值和不会变化的内部技术参数过度配置化。

### G-041 关键流程幂等、有限重试与补偿

支付、实名认证、验证码发送、文件上传、订单、权益或奖励发放、批量操作等高风险写入流程必须具备幂等、明确状态、有限次数重试、失败记录和人工可补偿入口。普通读取接口不得为了形式引入复杂任务系统；禁止无限重试和重复发放。

### G-042 依赖锁定与可重复构建

JDK、Gradle、Android Gradle Plugin、Kotlin、Compose、后端运行时、数据库版本和第三方依赖必须锁定并登记；每个 APK 和部署版本必须绑定 Git Commit、构建命令、签名配置和 SHA-256。不得在开发过程中无理由升级工具链或依赖导致构建漂移。

### G-043 自研图形安全验证码与匿名接口防刷

所有项目必须提供后端自研图形安全验证码能力，不接第三方。管理后台每次登录提交必须使用；当项目存在 App 登录、验证码登录、注册、找回或重置密码、发送邮箱/短信验证码等高风险匿名写接口时，每一个受保护提交都必须先弹出图形验证码，验证通过后才允许后端继续业务请求。验证码票据必须短时、一次性、用途和目标绑定，禁止跨动作复用，并配合 IP、服务端匿名会话、设备、账号或目标频控；正确答案不得返回客户端、写入日志或明文持久化。强制保护动作不得由普通后台配置关闭。

### G-044 复杂度预算与触发式开发

企业级标准是质量标准，不是无限增加功能数量。未被项目需求或依赖明确触发的平台模块不得开发；允许预留接口和边界，但禁止为了“以后可能需要”完整建设 BI、灰度平台、工作流引擎、全链路追踪、完整离线系统等重型能力。默认每个小版本最多新增一个平台型模块，核心业务闭环优先。

### G-045 增量验收与阶段全量回归

每个小版本必须完整测试新增页面、修改页面和受影响流程，并对未修改主流程执行必要冒烟；阶段版本和最终版本再执行全量页面、关键流程和视觉回归。不得因为全量重复测试拖慢每个小改动，也不得以“增量测试”为由跳过受影响范围或最终全量验收。


### G-046 页面返回状态保持与禁止无故重载

任何 Android App、管理后台、H5、弹窗、列表、详情、Tab 页面以及外部应用或系统选择器返回链路，用户进入下一页面后返回时，必须恢复离开前的可见状态和操作上下文，包括滚动锚点与偏移、Tab、筛选、搜索词、排序、分页或游标、展开收起、选择状态、输入草稿、已加载数据和局部错误状态。禁止无条件重新创建来源页面、滚回顶部、清空内容、出现全屏白屏，或因 `onResume`、路由返回、重新组合而再次全量请求。应使用返回栈和页面级状态容器；确需刷新时优先保留现有内容进行后台刷新并局部合并。只有用户主动刷新、登录或权限失效、数据已删除或不可继续展示、明确业务变更或安全要求等情况允许重置，且必须在页面规格中声明。支付 App、相机、相册、文件选择器和系统权限页面返回时同样执行。进程重建时至少恢复可安全持久化的路由、筛选、草稿和列表位置，敏感信息按安全规则处理。

### G-047 专业 SVG 图标体系与禁止文字代图标

所有用于表达导航、操作、状态、业务分类、支付方式和品牌入口的视觉图标必须使用真实图形资产。禁止把单个汉字、字母、数字、标点、货币符号、Emoji 或 Icon Font 字形置于圆形、方形或其他容器内充当图标，例如“支”“微”“A”“1”“￥”。默认通用功能图标采用项目统一的 Remix Icon SVG 线性/填充体系；第三方品牌优先使用官方品牌图标；项目专属功能使用独立设计的 SVG。官方品牌资产无法合法取得时，使用中性的业务类别 SVG 图标并配合正常文字标签，禁止伪造品牌图标。每个图标必须登记 Icon ID、语义、来源、授权或品牌来源、文件路径、尺寸、状态、深色模式和无障碍说明；同一项目禁止混用风格明显不一致的图标族。最终项目包必须包含实际使用的 SVG 源文件，并转换为 Android Vector/Compose 资源，管理后台和 H5 复用同一图标源。文字可以作为图标旁的标签，但不得替代图标。
